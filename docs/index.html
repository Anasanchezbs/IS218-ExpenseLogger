1. Research question and audience

Question: How should a small expense logger for college students store money amounts correctly and make sure each student only sees their own expenses?

Audience: my IS218 classmates and instructor, and me later in the semester when I build the app. I write for someone who knows basic web ideas but isn't an expert programmer.

Why these two questions: the whole app depends on them. If money math is wrong, the dashboard totals are wrong. If privacy is wrong, one student could see another student's spending.

4. Decision: how to store money

Approaches compared

ApproachProsCons
Float (Python float, Postgres double precision)Simple, fastInexact: 0.10 + 0.20 ≠ 0.30. Totals can drift.
Integer cents (store $4.99 as 499)Exact and fastEasy to forget to convert; every display needs ÷100
Decimal + NUMERIC(10,2) (chosen)Exact; reads like real money ("4.99")Slower — doesn't matter at student-app scale

Fact Python and PostgreSQL docs both say binary floats are inexact and recommend exact decimal types for money.

Interpretation For a small app, readability matters more than speed, so Decimal/NUMERIC beats integer cents for me.

Assumption One currency (US dollars) only. Amounts under $100,000,000 (NUMERIC(10,2) allows up to 99,999,999.99).

Check I ran

observed November 12, 2026, Python 3.13:

float   0.10 + 0.20         = 0.30000000000000004
float   0.10 + 0.20 == 0.30 → False
Decimal 0.10 + 0.20         = 0.30
Decimal equal to 0.30       → True

Surprise: adding ten 0.10 floats with sum() printed exactly 1.0. Newer Python versions make sum() more accurate, so the float problem doesn't show up in every case. The simple + case still fails, so the decision stands.

5. Decision: keeping each student's expenses private

ApproachRisk
Browser sends user_id and the server trusts itAnyone can change the number and read someone else's expenses
Server gets the user from the login token and filters every query by it (chosen)Low — the user can't pick whose data they get

Fact OWASP ranks broken access control as the #1 web application risk.

Interpretation Every expense query must include "belongs to the logged-in user," and asking for someone else's expense should return "not found" (404), so the app doesn't even confirm the expense exists.

Assumption No admin role or shared budgets in this version, which keeps the rules simple.

Passwords: hashed with Argon2 via pwdlib, following the FastAPI tutorial and OWASP guidance. Plain passwords are never stored.

6. Project plan

Finished flow

Account (sign up / log in) → useful interaction (log an expense) → saved record (expense stored in database) → private dashboard (my month, totals by category, history list) → account-update promise (change email/password, delete account and all my expenses).

Stack

Python 3 · FastAPI · PostgreSQL · SQLAlchemy · Pydantic · pytest · simple HTML templates · Docker Compose and GitHub Actions if the course setup uses them. Assumption This matches the class's expected stack; I'll confirm it against the project instructions.

Five user stories

  1. As a new student, I want to create an account with my email and a password so my spending stays private.
  2. As a student, I want to log an expense (amount, category, date, note) in under 30 seconds so I actually keep doing it.
  3. As a student, I want my expenses saved so they're still there next time I log in.
  4. As a student, I want a dashboard with this month's total and totals by category so I can see where my money goes.
  5. As a student, I want to change my email or password, or delete my account and all my data, so I stay in control.

Uncertain creative experiment (pattern experiment)

Idea: suggest a category automatically from the note ("chipotle" → Food, "NJ Transit" → Transportation).

Pattern: Strategy pattern. A CategorySuggester interface with two swappable versions: (1) KeywordSuggester using a fixed word list, and (2) HistorySuggester that reuses the category this student picked last time for a similar note.

Why it's uncertain: I don't know whether simple rules are accurate enough to help or just annoying.

How I'll judge it: on 20 sample expenses, does either version guess right at least 15 times? If not, the feature stays optional or gets cut. planned
